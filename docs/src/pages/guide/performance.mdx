# Bytecode size and gas

Lithe's restrictions make its programs easier to compile, as well as easier to review. Across the benchmark suite, Lithe's runtime bytecode is **about 33% smaller** than the best of five optimized `solc` builds of the equivalent Solidity. Every one of the 51 contracts comes in smaller, most by 20–45%.

The builds are `--via-ir` with 1, 200, 10,000, and 1,000,000 optimizer runs, and the legacy pipeline with 200 runs. The high run counts trade size for gas, so they set the bar for the gas comparison below. All are compiled `--no-cbor-metadata`, so metadata doesn't count against Solidity. Solar appends no metadata, and its builds are `-Ogas` and `-Osize`.

Solar is the closer comparison. Its size build is about 6% smaller than Lithe across the suite, and smaller on 31 of the 51 contracts. Lithe is still about 6% smaller than Solar's gas build. Lithe weighs bytes against gas, so it gives up some bytes to save gas on code that runs often.

Smaller code means cheaper deployment, and more room under the EIP-170 contract size limit of 24,576 bytes. A contract that still doesn't fit can [run modules from shared facets](/tooling/size-limit). Deployment gas falls with it: about 19% across the suite, 22% for the ERC-20, 33% for the ERC-721, and 38% for the Uniswap v2 factory. Each contract is set up as it deploys, by a `deploy` in Lithe and a constructor in Solidity, with the same arguments.

## Gas per transaction

Storage reads and writes dominate the cost of most transactions, and both compilers touch the same slots, so what separates them is everything else a transaction runs: dispatch, argument decoding, arithmetic, loops, memory, hashing, and encoding. On that part Lithe spends **about a third less gas** than the best `solc` build of each contract, and about 6% less in total execution gas, or 2% leaving out the pairs the Uniswap factory deploys. Of the 1,577 transactions and calls in the suite, Lithe costs less than every `solc` build on 1,257, the same on 197, and more on 123, most of those by under 2%. Solar is about even with Lithe: its gas build spends 0.1% less in total. Against the cheaper of Solar's two builds, Lithe costs more on 784 transactions, 747 of them by under 1%, the same on 242, and less on 551. Solar's total lead comes from the Uniswap factory, whose `createPair` deploys a pair 364 bytes smaller in Solar's gas build. Without those two transactions, Lithe spends less in total. The compiler weighs each choice between smaller and faster code by an estimate of how often the code runs, so a hot path can spend a few bytes to save gas on every call.

Some transactions still cost more than their Solidity versions. A transition that defers an external call runs its storage writes first, so when the call then reverts, those writes were paid for. A Solidity contract that makes the call before writing reverts sooner.

## The comparison is like for like

Most of the benchmark contracts are real programs, not microbenchmarks:

- **erc20**: OpenZeppelin's wizard token, burnable, pausable, and ownable, on the upgradeable contracts deployed without a proxy
- **erc20_full**: the wizard token with every common add-on: roles for minting and pausing, a cap, permits, votes with delegation and a checkpointed history, and flash loans through a borrower contract
- **erc721**: OpenZeppelin's wizard NFT with the same extensions, plus `safeTransferFrom` against a receiver contract
- **erc721_full**: the wizard NFT with every common add-on: enumeration, URI storage with a base URI, burning, pausing, auto-increment minting, and ERC-2981 royalties
- **erc1155**: OpenZeppelin's wizard multi-token, burnable, pausable, and ownable, with supply tracking and an updatable URI
- **erc4626**: OpenZeppelin's `ERC4626` vault
- **erc6909**: OpenZeppelin's `ERC6909` with its token supply, metadata, and content URI extensions, built from the standard library's modules, whose storage sits at their own ERC-7201 roots, so its slots are left out like Solady's
- **staking**: Synthetix's `StakingRewards` on OpenZeppelin's `Ownable` and `Initializable`
- **uniswap_v2_factory** and **uniswap_v2_pair**: Uniswap v2-core, ported to Solidity 0.8, with the factory creating each pair with `CREATE2`. A pair lands at a different address in each build, so the comparison names it by role, and swaps both ways, liquidity, the protocol fee, and a signed permit replay on each
- **fixed_point**, **date_time**, and **base64**: Solady's `FixedPointMathLib`, `DateTimeLib`, and `Base64`, next to Lithe's standard library
- **deployers** and **safe_erc20**: OpenZeppelin's `Clones` and `SafeERC20`, and Solady's `SSTORE2` and `CREATE3`
- **executor** and **exchange**: calls whose results feed continuations
- **records** and **layout**: packed records, fixed lists, and tuples in storage
- **solady_erc20**, **solady_erc721**, and **solady_erc1155**: Solady's hand-written assembly tokens, with EIP-2612 permits and the Permit2 allowance on the ERC-20, and safe transfers against receiver contracts on the others, next to plain Lithe with the same errors, events, and order of checks

The rest each exercise one part of the language: strings, lists, records, logs, loops, ABI encoding, low-level calls, and errors.

Each Solidity version uses OpenZeppelin where the original does. The benchmark deploys every build of every contract to a local chain and replays the same transactions against each one. It then checks that **statuses, return data, logs, and every storage slot** agree across all eight builds. Lithe lays out storage exactly as Solidity does, so the raw slots have to match byte for byte. Solady's tokens are the exception: they put each value at a hashed slot of their own, which no Solidity layout produces, so their slots are left out and everything else is still compared.

## Reproducing

The benchmark needs [Foundry](https://getfoundry.sh) (`anvil` and `cast`) and `solc`. Set `SOLC` to pick a specific binary. The Solar builds run when `solar` is on the path, or when `SOLAR` names the binary. From the repository root:

```bash
cargo build --release
python3 bench/run.py            # every contract
python3 bench/run.py erc20      # one contract
```

The Lithe and Solidity sources are side by side in `bench/`: `erc20.lithe` next to `erc20.sol`, and so on. A contract answers ERC-165 only where it implements it, in both languages: `erc721`, `erc1155`, `erc6909`, and `erc20_full` list their standards in `supports`, and `erc721_full` writes its own `supportsInterface` to add ERC-4906.

These numbers come from the compiler version this site was built with. Rerun the benchmark for current figures.
