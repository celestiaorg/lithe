# Modules and contracts

Lithe has no inheritance. Reusable behavior lives in **modules**, and a **contract** composes modules explicitly.

## Modules

A module groups storage, types, errors, events, and functions under one name:

```lithe fragment
module Ownable is {
  storage ownable at "example.ownable" is record {
    owner : address;
  }

  error Not_owner;

  event Ownership_transferred of record {
    indexed previous : address;
    indexed next : address;
  }

  view function owner() : address is
    ownable.owner

  view function only_owner()
    raises Not_owner
  is {
    assert(Evm.sender() = ownable.owner, Not_owner);
  }

  function transfer_ownership(const next : address)
    raises Not_owner
  is {
    only_owner();
    emit Ownership_transferred { previous = ownable.owner; next = next; };
    ownable.owner := next;
  }
}
```

- A module's storage must be **named**. Inside the module it is `ownable.owner`. Everywhere else it is qualified with the module's name: `Ownable.ownable.owner`.
- A module's functions are internal. A module may also declare `external` functions: the interface it offers. A contract exposes them only by declaring them. See [Exposing a module's externals](#exposing-a-modules-externals).
- A module's errors and events keep their names, so contracts that use the module raise and log them under the standard signatures.

## Contracts

A contract `use`s modules, and exposes what a module offers in one of two ways: by **declaring** the module's externals, or by **wrapping** its functions in externals of its own.

```lithe
module Counter is {
  storage counter at "example.counter" is record {
    count : nat;
  }

  function bump(const by : nat) is {
    counter.count := counter.count + by;
  }

  (* The interface the module offers. *)
  external view function count() : nat is
    counter.count

  external function reset() is {
    counter.count := 0n;
  }
}

contract App is {
  (* Declaring exposes the module's externals as they are. *)
  external use Counter is {
    view function count() : nat;
  }

  storage is record {
    calls : nat;
  }

  (* Wrapping adds behavior around a module's functions. *)
  external function bump(const by : nat) is {
    storage.calls := storage.calls + 1n;
    Counter.bump(by);
  }

  external view function current() : nat is
    Counter.counter.count
}
```

`App` exposes `count`, `bump`, and `current`. It doesn't declare `reset`, so `reset` is not part of its interface. Nothing is exposed implicitly: every entrypoint a contract has is written in the contract, and if a module adds an external, no contract gains an entrypoint until it declares it.

## Exposing a module's externals

`external use M is ...` uses `M`, as `use M` does, and names the [interfaces](/language/effects#interfaces) whose methods the contract exposes from `M`: named ones, an inline one in braces, or both. Each method must be one of `M`'s externals:

```lithe fragment
external use ERC20 is IERC20, IERC20Metadata;

external use ERC20Permit is IERC20Permit, {
  view function nonces(owner : address) : nat;
}
```

A method is an external's header as an interface writes it: no `external`, `name : type` parameters, and `;` in place of the body. It must match the module's external:

- the name and parameter types pick one external. An overloaded external is exposed once for each overload the interfaces list
- the parameter names and result must match
- the effect must match: `view`, `pure`, or stateful. So must `payable`: a module's `external payable function` is exposed as `payable function`
- `raises` must list the same errors. A named error set counts as its members

`nonreentrant`, and whether a parameter is `const` or `var`, are how the module defines the external, so an interface doesn't repeat them. A module appears in one `external use`, which lists all its interfaces. For part of an interface, declare the part inline, or as an interface of its own.

A declaration that differs is an error that shows both headers:

```lithe rejects
module Ledger is {
  storage ledger at "example.ledger" is record {
    n : nat;
  }

  external view function balance() : nat is
    ledger.n
}

contract Token is {
  external use Ledger is {
    function balance() : nat;
  }
}
```

```text
`balance` does not match its declaration in module `Ledger`

  module:   view function balance() : nat
  contract: function balance() : nat
```

An interface never adds behavior, so its methods have no body. To change what an external does, leave it out of the contract's interfaces, and write the contract's own external instead. A module's externals are not functions: nothing inside the contract calls them. Put shared logic in an internal function that the external and the contract both call.

When a contract is over the [size limit](/tooling/size-limit), a module it exposes can run from the module's **facet**, compiled from the module alone and shared by every contract that exposes it. The interfaces' methods are what the router forwards to it. `lithe stubs file.lithe M` prints an `external use` block with every external `M` has.

## ERC-165

Every contract answers ERC-165's `supportsInterface(bytes4)`: true for ERC-165 itself, and for each interface the program declares or imports that the contract has. A contract has an interface when it dispatches every one of the interface's methods, with the same result, whether they come from `external use` or from its own externals. Nothing says a contract has an interface; it just does, as with Go's interfaces. An interface's id is the XOR of its methods' selectors, so the standard library's `IERC721`, for example, answers for `0x80ac58cd`. Inline interfaces have no name, and no id of their own.

A contract that writes its own `supportsInterface` keeps it, and the compiler warns when there are interfaces it has that the compiler would have answered for. `--erc165 off` turns the generated function off; it costs about 43 bytes, and a few more for each interface the contract has.

## Dependencies between modules

A module that calls another module, or reads its storage, declares it with `requires`. A contract that uses the dependent module must also use every module it requires. A module can call only its own functions and those of the modules it requires, never a function of the contract that uses it, so its code is the same in every contract:

```lithe
module Pausable is {
  storage pausable at "example.pausable" is record {
    paused : bool;
  }

  error Paused;

  view function when_not_paused()
    raises Paused
  is {
    assert(not pausable.paused, Paused);
  }

  external function pause() is {
    pausable.paused := true;
  }
}

module Ledger is {
  requires Pausable;

  storage ledger at "example.ledger" is record {
    balances : map(address, nat);
  }

  error Insufficient of nat;

  external function transfer(const to : address; const amount : nat)
    raises Paused | Insufficient
  is {
    Pausable.when_not_paused();
    const have : nat := ledger.balances[Evm.sender()];
    assert(have >= amount, Insufficient(have));
    ledger.balances[Evm.sender()] := have - amount;
    ledger.balances[to] := ledger.balances[to] + amount;
  }

  (* Reading a required module's storage is allowed. *)
  external view function frozen() : bool is
    Pausable.pausable.paused
}

contract Token is {
  external use Pausable is {
    function pause();
  }

  external use Ledger is {
    function transfer(to : address; amount : nat)
      raises Paused | Insufficient;
    view function frozen() : bool;
  }

  storage is record {
    admin : address;
  }
}
```

```lithe rejects
module Ledger is {
  storage ledger at "lithe.ledger" is record {
    n : nat;
  }

  function set(const n : nat) is {
    ledger.n := n;
  }
}

module Guarded is {
  requires Ledger;

  external function set(const n : nat) is {
    Ledger.set(n);
  }
}

contract Token is {
  external use Guarded is {
    function set(n : nat);
  }
}
```

```text
module `Guarded` requires `Ledger`
```

## Qualified storage

Outside its module, a module's storage is always written with the module's name, so a reviewer can see whose state is being touched:

```lithe rejects
module Ledger is {
  storage ledger at "lithe.ledger" is record {
    n : nat;
  }

  function set(const n : nat) is {
    ledger.n := n;
  }
}

contract Token is {
  use Ledger;

  external function go(const n : nat) is {
    ledger.n := n;
  }
}
```

```text
storage `ledger` belongs to `Ledger`; write `Ledger.ledger`
```

Reaching into a module's storage like this is allowed, but calling the module's functions is usually clearer, because they maintain its invariants. Because every module's storage sits at its own ERC-7201 root, modules compose without slot collisions. Two modules that claim the same storage id are rejected.

## Extension modules

An extension adds behavior and its own storage on top of a base module, without changing the base:

```lithe fragment
module ERC20Votes is {
  requires ERC20;

  storage votes at "lithe.std.erc20.votes" is record {
    delegates : map(address, address);
  }

  function delegate(const delegatee : address) is {
    votes.delegates[Evm.sender()] := delegatee;
  }
}
```

The contract that uses `ERC20` and `ERC20Votes` decides whether a transfer should also move votes, and says so in its own `transfer`. An extension cannot silently change the base's behavior.

Modules are usually written in their own files and brought in with `import`. See [Imports](/language/imports). Modules can also take type parameters. See [Generics](/language/generics).
