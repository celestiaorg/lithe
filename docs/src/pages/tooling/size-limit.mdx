# Contract size limit

[EIP-170](https://eips.ethereum.org/EIPS/eip-170) caps deployed code at 24,576 bytes. Lithe never moves code out of a contract on its own. You choose what runs elsewhere, by marking a module `delegated` where the contract uses it. A marked module runs from its **facet**, a contract of its own that is built from the module alone and shared by every contract that marks it. The contract that uses it becomes a **router**. Callers still see one contract: one address, one ABI, and the same return data, logs, and errors.

A contract that marks nothing compiles as it always does, byte for byte. When it is over the limit it still compiles, with a warning that says what takes the space and what marking each module would save. Only a contract over 65,535 bytes, which can't be assembled at all, is an error.

## Marking a module

`delegated` goes right after the module's name in a `use`, before `exposing` and the interfaces it exposes:

```lithe
import "std/evm";

module Ledger is {
  storage ledger at "example.ledger" is record {
    balances : map(address, uint);
    total : uint;
  }

  error Short of uint;

  event Minted of record {
    indexed to : address;
    amount : uint;
  }

  pure function fee(const amount : uint) : uint is
    amount * 30 / 10_000

  view function balance(const who : address) : uint is
    ledger.balances[who]

  function mint(const to : address; const amount : uint) is {
    ledger.balances[to] := ledger.balances[to] + amount;
    ledger.total := ledger.total + amount;
    emit Minted { to = to; amount = amount; };
  }

  function burn(const from : address; const amount : uint)
    raises Short
  is {
    const have : uint := ledger.balances[from];
    assert(have >= amount, Short(have));
    ledger.balances[from] := have - amount;
    ledger.total := ledger.total - amount;
  }

  external view function total() : uint is
    ledger.total
}

contract Bank is {
  use Ledger delegated exposing {
    view function total() : uint;
  }

  storage is record {
    deposits : uint;
  }

  external payable function deposit() is {
    const amount : uint := uint(Evm.value());
    Ledger.mint(Evm.sender(), amount - Ledger.fee(amount));
    storage.deposits := storage.deposits + 1;
  }

  external function burn(const amount : uint)
    raises Short
  is {
    Ledger.burn(Evm.sender(), amount);
  }

  external view function balance() : uint is
    Ledger.balance(Evm.sender())
}
```

A module the contract uses without exposing anything is marked the same way: `use Ledger delegated;`. An unmarked module is always part of the contract.

A delegated module and a [`fallback` that `delegates to`](/language/functions#passing-a-call-on) both run code that lives elsewhere as this contract, on its storage. The difference is where that code comes from: a delegated module's facet is built by the compiler from the module's own source, at an address derived from that code, and is reachable only through the router, while `delegates to` goes wherever its target expression says.

## What runs where

`delegated` means the module's code never lives in the contract. Everything the module does, the contract reaches in its facet:

- **Its externals.** For each one the contract exposes, the router forwards the call to the facet with `delegatecall`, so the facet runs on the router's storage, balance, and address. A [guarded](/language/modules#guards) external runs the contract's check in the router first.
- **Its functions, called from the contract's own code.** An entrypoint, a view, `deploy`, a migration, a guard, or a continuation that calls one of the module's functions calls it across, in the facet. A `pure` function is called with `staticcall`. A `view` or stateful one is called with `delegatecall`, so it reads and writes the contract's storage, and its events are the contract's. A `view` entrypoint can call a view function across: `delegatecall` is allowed inside a `staticcall`, and the function writes nothing.

In the example, `deposit` calls `Ledger.fee` with `staticcall` and `Ledger.mint` with `delegatecall`, and `balance` calls `Ledger.balance` with `delegatecall` too. Each call ABI-encodes its arguments, the facet runs the function, and the result is decoded where the function's result would have been. When the function fails, the contract reverts with the facet's revert data, so its errors and panics reach the caller unchanged. What a function does is the same as it would be inline: the same results, errors, events in the same order, and storage.

The module's constants, pure functions with no parameters, are values, and fold into the contract as they always do. A function that writes the module's [immutables](/language/storage#immutables) runs in the contract too: only `deploy` and migrations can call it, and they are where the contract's immutables are written.

A module's externals are still not functions: nothing inside the contract calls them, delegated or not.

### What can be called across

A function can be called across when its parameters and result are ABI values, the values an external can take and return. These can't:

- a generic function
- a function with a `storage` parameter, or a parameter or result that is an `option`, a map, or a variant with payloads
- a function that `defer`s, or calls one that does. A deferred call runs after the whole transition commits, and the facet's run of the function is its own
- a `view` or stateful function that reads the call's calldata with `Evm.calldata()` or `Evm.selector()`, since its facet sees its own

A call to one is an error that names the function and the reason:

```lithe rejects
import "std/evm";

module Book is {
  storage book at "example.book" is record {
    pages : map(uint, uint);
  }

  function write(storage pages : map(uint, uint); const k : uint) is {
    pages[k] := 1;
  }
}

contract Shelf is {
  use Book delegated;

  storage is record {
    mine : map(uint, uint);
  }

  external function note(const k : uint) is {
    Book.write(storage.mine, k);
  }
}
```

```text
`Book.write` runs in `Book`'s facet, and contract code can't call it across: its parameter `pages` is a storage reference; move the call into `Book`, or use `Book` without `delegated`
```

A `view` or stateful function in the facet sees storage as it is when it is called. A body that runs a [query](/language/effects#query) after writing storage keeps its writes until it ends, so that the query sees storage as the transition found it. Such a body can't call a `view` or stateful function across, since the function wouldn't see the writes:

```lithe rejects
module Book is {
  storage book at "example.book" is record {
    pages : map(uint, uint);
  }

  function note(const k : uint; const v : uint) is {
    book.pages[k] := v;
  }
}

interface Oracle is {
  view function price() : uint;
}

contract Shelf is {
  use Book delegated;

  storage is record {
    n : uint;
  }

  external function note(const oracle : Oracle) is {
    storage.n := storage.n + 1;
    Book.note(storage.n, query oracle.price());
  }
}
```

```text
`Book.note` runs in `Book`'s facet, which sees storage as it is when called, but a body that calls it runs a query after writing storage, so it keeps its writes until it ends; query before the first write, or use `Book` without `delegated`
```

### The facet's own entrypoints

A facet has an entrypoint for each function of its module that contract code can call across, whether or not a given contract calls it. A module's [`private`](/language/modules#delegated-modules) functions are only for its own code, so they have none, which keeps a facet's helpers from costing it bytes. Their names can't be written in source and no ABI lists them, so no external of the module can collide with one. The router never dispatches their selectors: it forwards only the externals the contract exposes, and a call with any other selector reaches the contract's own code, or reverts. Called directly, a facet runs against its own storage, not the storage of any contract that uses it, so there is nothing there to protect. The same argument covers guards: a facet runs its module's externals unguarded, which is what lets contracts with different guards share it.

## Sharing

A facet is built from its module alone: the module's externals, an entrypoint for each function contract code can call across, and copies of the modules it `requires`. None of the contract is in it, so it doesn't matter which contract marks the module, which of its externals the contract exposes, or which of its functions the contract calls. **Every contract that marks the same module gets the same facet at the same address**, so ten collections built on the same modules deploy each facet once. A facet changes, and moves to a new address, only when its module or a module it requires changes.

Two facets never call each other. A module that requires another carries a copy of it in its facet, whether or not the contract marks that one too, and calls it there. Storage is shared all the same: each module's storage sits at its own ERC-7201 root, the same in the router and in every facet, and a module's transient storage sits at a slot derived from its name.

## Over the limit

A contract over `--size-limit` still compiles and emits its bytecode, with a warning. It lists what takes the space: the contract's own entrypoints, by group, and for each module the contract runs in its own code, what marking it `delegated` would save. Here the [standard-library token](/stdlib/tokens), with no modules marked, is built with `--size-limit 2000`:

```text
token.lithe:16:1: warning: contract `Token` is 2,894 bytes; the limit is 2,000
  ERC20                       758
  Token                       621
  ERC20Permit                 526
  Ownable                      89
  ERC20Burnable                83
  Pausable                      1
  (dispatch and shared code)  816

each module's row is what the contract saves when the module runs from its own facet contract instead: mark it with `use M delegated;` or `use M delegated exposing ...;`. The contract's own row is its entrypoints, which stay in it
```

A module that can't be a facet says why instead of a number, such as `can't be a facet: it is generic`, or which of its functions the contract calls that can't be called across. A facet over the limit gets a warning of its own. Creation code has a limit of twice `--size-limit`, as [EIP-3860](https://eips.ethereum.org/EIPS/eip-3860) allows, and a contract or a facet over that is warned about the same way.

Before any of that, the compiler fits a contract by outlining: code the contract repeats becomes shared subroutines, as few as it takes to fit. That changes code, not what runs where, so it never needs a mark.

## Immutables

A facet's code is shared, so it can't have one contract's [immutables](/language/storage#immutables) built in. It reads them from its router instead. For each call it forwards, and each call across, the router appends the values of every immutable block the facet has, its module's and those of the modules it requires, after the calldata, blocks in order of their ids. A plain router keeps them in its own code, where its creation code writes them. An upgradeable router loads them from the proxy's storage. A forwarded call whose code reads no immutable gets words of the same length without the values, so it pays for neither. The facet reads each from the end of its calldata, and everything in it that reads the calldata or its size, such as the ABI decoder or `Evm.calldata()`, sees the calldata without them. What a facet reads is fixed by its module alone, so its address still depends only on its code.

## Seeing what runs where

`lithe facets` shows the router and each facet, with the size of each against the limit:

```bash
lithe facets token.lithe --size-limit 2000
```

```text
router  1,630 / 2,000
  Token: transfer, transferFrom, mint, pause, unpause, supportsInterface
  ERC20Burnable: burn, burnFrom
  Ownable: transferOwnership, renounceOwnership, owner
  Pausable: paused

facet ERC20  0x13F9822a430D5E4E70Af364A11350407Be3bBD81  2,217 / 2,000
  approve, name, symbol, decimals, totalSupply, balanceOf, allowance
  called across: ERC20.init, ERC20.total_supply, ERC20.move, ERC20.mint, ERC20.burn, ERC20.spend_allowance
  (2 more externals this contract does not declare)

facet ERC20Permit  0x04d7e8AfDE9737f054132c9eEAD1E05d275Fd0DA  739 / 2,000
  permit, nonces, DOMAIN_SEPARATOR
```

That is the same token with `delegated` on its `ERC20` and `ERC20Permit` uses. Under each facet are the externals the router forwards to it, and then the module's functions the contract's code calls across. A facet holds every external its module declares; the router forwards only the ones the contract declares, so the others can't be reached through it. `lithe footprint` and `lithe abi-tree` also show where each entrypoint runs.

## Deploying

Each facet is deployed with `CREATE2` through the deterministic deployment proxy at `0x4e59b44847b379578588920cA78FbF26c0B4956C`, the same factory Foundry uses, with a zero salt. So a facet's address depends only on its code. The compiler knows every address in advance and builds them into the router. The router can only ever reach the exact code it was compiled against. Contract code reads a facet's address as a constant with `Evm.facet_address(M)`, for a view that reports it, or a registry that lists it.

For a contract with facets, `lithe compile` prints the deployment plan instead of bytecode, with a note on stderr:

```text
note: `Token` runs `ERC20`, `ERC20Permit` from their facets
```

```json
{
  "facets": [
    {
      "name": "ERC20",
      "address": "0x13F9822a430D5E4E70Af364A11350407Be3bBD81",
      "to": "0x4e59b44847b379578588920cA78FbF26c0B4956C",
      "data": "0x0000…"
    },
    …
  ],
  "router": {
    "bytecode": "0x34…"
  }
}
```

The plan lists exactly the facets the source marks. Send each facet's `data` to its `to`, in order, then deploy the router's `bytecode` as you would any creation code, with its `deploy` arguments appended. Skip a facet whose address already has code, because another contract already deployed it: `CREATE2` can't deploy to it twice, and it is already the right code. The router's creation code checks that every facet has code, and reverts if one is missing. `deploy` can call its facets' functions across as the router's code can.

An upgradeable router is listed with its own `address`, `to`, and `data`, so it can be deployed through the factory too, at an address known in advance.

A contract that creates a contract with facets, with `defer create`, lists that contract's facets in its plan as well. They must exist before it creates anything.

`lithe compile directory` writes the router's artifact to `out/<file>/<Contract>.json` as usual. Its ABI is the whole contract's, because that is what callers use, and it gains a `facets` field listing each facet's module, address, and the selectors the router forwards to it. Each facet gets one artifact, `out/facets/<Module>.json`, shared by every contract in the directory that uses it. A facet's artifact lists its module's externals; the entrypoints for calls across are in its bytecode, but in no ABI.

## Upgrades

An upgradeable contract's router is the implementation behind its ERC-1967 proxy. Its upgrade guard is the only way to change code, and an upgrade is still one `upgradeToAndCall`. Facets never answer the upgrade entrypoints: `proxiableUUID`, `upgradeToAndCall`, and every migration run in the router. Facets are deployed first, and deploying them changes nothing until the proxy points at the new router.

Marking a module `delegated`, or unmarking it, is an upgrade like any other: the new router runs the module from its facet, or in its own code, behind the same proxy, at the same address, with the same storage.

Every upgrade of a contract with facets deploys a new router, because the router has its facets' addresses built in. A facet whose module didn't change keeps its address and is reused. `lithe upgrade-check` shows which:

```text
facets
  router       changed
  ERC20        unchanged  0x13F9822a430D5E4E70Af364A11350407Be3bBD81
  ERC20Permit  new        0x88a0…

compatible
```

For a contract with facets, `lithe upgrade` prints the deployment plan with the proxy's `upgradeToAndCall` added, and `--impl` defaults to the new router's `CREATE2` address.

## Cost

A call to an external that runs in a facet costs one extra `delegatecall`, measured at about 2,700 gas: the facet's address is cold, and the calldata and return data are copied once more. A call whose code reads immutables costs a little more, for copying them, and behind a proxy the router reads each word of them from storage. A guarded external also decodes its arguments in the router, for the guard, before the facet decodes them again.

A call across costs a `staticcall` or `delegatecall`: about 2,600 gas the first time a transaction reaches the facet, for the cold account, and 100 after that. It also pays for encoding its arguments, the facet decoding them and encoding its result, and decoding that. A result that is a large value costs more again, since the caller decodes and copies it into its own memory. The function's own work costs what it would inline. A function called across in a loop pays on every run, so a module the contract calls from a hot loop may be cheaper unmarked.

Each facet carries its own dispatcher and a copy of the modules it requires, so a single contract with facets deploys more bytes in total than its build without them. Contracts that share facets deploy them once.

## Flags

| Flag | Default | Meaning |
| --- | --- | --- |
| `--size-limit <bytes>` | `24576` | the most runtime code the router or any facet should have. Creation code may have twice this, as EIP-3860 allows. Code over it still builds, with a warning |
| `--create2-deployer <address>` | `0x4e59…956C` | the `CREATE2` factory facets are deployed through, for chains where it lives elsewhere |

`compile`, `facets`, `footprint`, `abi-tree`, `upgrade`, and `upgrade-check` take them.

`lithe stubs file.lithe Module` prints the `use Module exposing` block that declares every external a module has, to copy into a contract and trim.
