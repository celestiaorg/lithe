# Contract size limit

[EIP-170](https://eips.ethereum.org/EIPS/eip-170) caps deployed code at 24,576 bytes. When a contract is over the limit, the compiler moves the modules it exposes with [`use M exposing`](/language/modules#exposing-a-modules-externals) into **facets**, and keeps the rest in a **router**. Callers still see one contract: one address, one ABI, and the same return data, logs, and errors.

A contract that fits compiles exactly as it always does, byte for byte.

## How a split contract works

```text
caller ──call──▶ router ──delegatecall──▶ ERC20 facet · ERC20Permit facet · ...
```

The router runs what the contract writes itself, its upgrade machinery, and any exposed module that stays inline. For every selector a moved module provides, it forwards the call to that module's facet with `delegatecall`, so the facet uses the router's storage, balance, and address. Nothing about storage changes: module storage stays at its ERC-7201 root, and the default record stays at slot 0. Events are logged from the router's address, and a facet's errors reach the caller unchanged.

A facet is built from its module alone: the module's externals, and the modules it `requires`. None of the contract is in it, so it doesn't matter which contract exposes the module, which of its externals the contract declares, or what else the contract does. **Every contract that exposes the same module gets the same facet at the same address**, so ten collections built on the same modules deploy each facet once. A facet changes, and moves to a new address, only when its module or a module it requires changes.

A module's [guards](/language/modules#guards) are the contract's code, so they run in the router: for a guarded external, the router decodes the call's arguments and runs the contract's check before it forwards the call. The facet runs the module's externals unguarded, which is what lets contracts with different guards share it. Called directly, a facet runs against its own storage, so skipping the router's guards there changes nothing of any contract's.

This is safe because a module never depends on the contract that uses it: its storage is its own, it can call only the modules it requires, and a module's transient storage sits at a slot derived from its name. Continuations run in the frame that deferred the call.

## Immutables

A facet's code is shared, so it can't have one contract's [immutables](/language/storage#immutables) built in. It reads them from its router instead. For each call it forwards, the router appends the values of every immutable block the facet has, its module's and those of the modules it requires, after the calldata, blocks in order of their ids. A plain router keeps them in its own code, where its creation code writes them, and copies them with one `CODECOPY`. An upgradeable router loads them from the proxy's storage. A call whose code reads no immutable gets words of the same length without the values, so it pays for neither. The facet reads each from the end of its calldata, and everything in it that reads the calldata or its size, such as the ABI decoder or `Evm.calldata()`, sees the calldata without them. What a facet reads is fixed by its module alone, so its address still depends only on its code.

## Which modules move

Only a module the contract exposes with `use M exposing` can move. What the contract writes itself always stays in the router, so a contract over the limit that exposes no modules is an error.

With `--split auto`, the default, the compiler first builds the whole contract. If it fits, that's the output. If not, it moves the module that saves the most bytes into its facet, then the next, until the router fits. With `--split all`, every exposed module runs from its facet even when the contract fits, so a set of contracts shares the same facets however large each one is.

`lithe facets` shows what runs where:

```bash
lithe facets token.lithe --size-limit 2000
```

```text
router  1,989 / 2,000
  Token: transfer, transferFrom, mint, pause, unpause
  ERC20Burnable: burn, burnFrom
  Ownable: transferOwnership, renounceOwnership, owner
  Pausable: paused

facet ERC20  0x2a69b5859Bd3dd4D83693b9CE6b60D29101A1fe0  1,438 / 2,000
  approve, name, symbol, decimals, totalSupply, balanceOf, allowance
  (2 more externals this contract does not declare)

facet ERC20Permit  0xCf7c2a6CeB11CBFAE62cEbE5D4268776a3E7CcE1  1,233 / 2,000
  permit, nonces, DOMAIN_SEPARATOR
```

That output is the [standard-library token](/stdlib/tokens), built with `--size-limit 2000` so that it splits. A facet holds every external its module declares; the router forwards only the ones the contract declares, so the others can't be reached through it. `lithe footprint` and `lithe abi-tree` also show where each entrypoint runs when the contract is split.

## Deploying

Each facet is deployed with `CREATE2` through the deterministic deployment proxy at `0x4e59b44847b379578588920cA78FbF26c0B4956C`, the same factory Foundry uses, with a zero salt. So a facet's address depends only on its code. The compiler knows every address in advance and builds them into the router. The router can only ever reach the exact code it was compiled against.

For a split contract, `lithe compile` prints the deployment plan instead of bytecode, with a note on stderr:

```text
note: `Token` is 3,395 bytes; `ERC20`, `ERC20Permit` run from their facets
```

```json
{
  "facets": [
    {
      "name": "ERC20",
      "address": "0x2a69b5859Bd3dd4D83693b9CE6b60D29101A1fe0",
      "to": "0x4e59b44847b379578588920cA78FbF26c0B4956C",
      "data": "0x0000…"
    },
    …
  ],
  "router": {
    "bytecode": "0x34…"
  }
}
```

Send each facet's `data` to its `to`, in order, then deploy the router's `bytecode` as you would any creation code, with its `deploy` arguments appended. Skip a facet whose address already has code, because another contract already deployed it: `CREATE2` can't deploy to it twice, and it is already the right code. The router's creation code checks that every facet has code, and reverts if one is missing.

An upgradeable router is listed with its own `address`, `to`, and `data`, so it can be deployed through the factory too, at an address known in advance.

A contract that creates a split contract with `defer create` lists that contract's facets in its plan as well. They must exist before it creates anything.

`lithe compile directory` writes the router's artifact to `out/<file>/<Contract>.json` as usual. Its ABI is the whole contract's, because that is what callers use, and it gains a `facets` field listing each facet's module, address, and the selectors the router forwards to it. Each facet gets one artifact, `out/facets/<Module>.json`, shared by every contract in the directory that uses it.

## Upgrades

An upgradeable contract's router is the implementation behind its ERC-1967 proxy. Its upgrade guard is the only way to change code, and an upgrade is still one `upgradeToAndCall`. Facets are deployed first, and deploying them changes nothing until the proxy points at the new router. `migrate` always runs in the router, inside the upgrade.

A contract that grows past the limit upgrades into a split implementation behind the same proxy, at the same address, with the same storage. The reverse works too.

Every upgrade of a split contract deploys a new router, because the router has its facets' addresses built in. A facet whose module didn't change keeps its address and is reused. `lithe upgrade-check` shows which facets are reused:

```text
facets
  router       changed
  ERC20        unchanged  0x2a69b5859Bd3dd4D83693b9CE6b60D29101A1fe0
  ERC20Permit  new        0x88a0…

compatible
```

For a split contract, `lithe upgrade` prints the deployment plan with the proxy's `upgradeToAndCall` added, and `--impl` defaults to the new router's `CREATE2` address.

## Cost

A call to an entrypoint in a facet costs one extra `delegatecall`, measured at about 2,700 gas: the facet's address is cold, and the calldata and return data are copied once more. A call whose code reads immutables costs a little more, for copying them, and behind a proxy the router reads each word of them from storage. Entrypoints in the router cost nothing extra. A guarded one also decodes its arguments in the router, for the guard, before the facet decodes them again. Each facet carries its own dispatcher and a copy of the modules it requires, so a single split contract deploys more bytes in total than its unsplit build would have. Contracts that share facets deploy them once.

## Flags

| Flag | Default | Meaning |
| --- | --- | --- |
| `--size-limit <bytes>` | `24576` | the most runtime code the router or any facet may have. Creation code may have twice this, as EIP-3860 allows |
| `--split <auto\|off\|all>` | `auto` | when exposed modules run from their facets: when the contract is over the limit, never, or always |
| `--create2-deployer <address>` | `0x4e59…956C` | the `CREATE2` factory facets are deployed through, for chains where it lives elsewhere |

`compile`, `facets`, `footprint`, `abi-tree`, `upgrade`, and `upgrade-check` take them. With `--split off`, a contract over the limit fails with what each module and the contract's own code add to its size:

```text
contract `Token` is 3,395 bytes; the limit is 2,000
  ERC20Permit                 1,077
  Token                         606
  ERC20                         596
  Ownable                       264
  ERC20Burnable                 174
  Pausable                       42
  (dispatch and shared code)    636
```

A contract is also an error when splitting can't fit it: when a module's facet is over the limit on its own, or when the router is, with every exposed module moved out. Then move more of the contract's entrypoints into modules.

`lithe stubs file.lithe Module` prints the `use Module exposing` block that declares every external a module has, to copy into a contract and trim.
