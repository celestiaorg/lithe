# Contract size limit

[EIP-170](https://eips.ethereum.org/EIPS/eip-170) caps deployed code at 24,576 bytes. When a contract is over the limit, the compiler splits it into a **router** and one or more **parts**. You don't change any source. Callers still see one contract: one address, one ABI, and the same return data, logs, and errors.

A contract that fits compiles exactly as it always does, byte for byte.

## How a split contract works

```text
caller ──call──▶ router ──delegatecall──▶ part 1 · part 2 · ...
```

The router keeps as many entrypoints as fit, and hands each of the other selectors to the part that runs it. Parts run with `delegatecall`, so they use the router's storage, balance, and address. Nothing about storage changes: module storage stays at its ERC-7201 root, and the default record stays at slot 0. Events are logged from the router's address, and a part's errors reach the caller unchanged.

This is safe because nothing in a Lithe contract depends on which code is running. Every part is compiled from the same contract, so it has the same storage layout, transient storage, and `nonreentrant` lock. Module functions are compiled into each part that uses them, so parts never call each other. Continuations run in the frame that deferred the call.

## Where entrypoints go

Entrypoints are placed in groups:

| Entrypoint | Group |
| --- | --- |
| `external function x is M.f` | the module `M` |
| written in the contract, a `migrate`, or an upgradeable contract's `deploy` | the contract |
| `proxiableUUID`, `upgradeToAndCall` | always the router |

The router takes the contract's group, then each module's group in `use` order, until the next group doesn't fit. Entrypoints in the router pay nothing extra per call. The remaining groups fill parts in the same order. A group that doesn't fit in the current part starts a new one. A group that doesn't fit in any part is split into its entrypoints. Placement depends only on the source and the flags, so a build always produces the same parts.

`lithe parts` shows the placement:

```bash
lithe parts token.lithe
```

```text
router  161 / 500

part 1  0x995142bb0A829AfDb6dC92D05D8D9395b12FA5Ca  426 / 500
  Token: guarded_transfer, safe_transfer, flag

part 2  0x3447969d9eEDD2491a9720a4c5b92Ee983fB7e4A  460 / 500
  Ledger: mint, transfer, balance_of
  Pausable: pause, is_paused
```

That output was produced with `--size-limit 500`, to split a small contract. `lithe footprint` and `lithe abi-tree` also show each entrypoint's part when the contract is split.

## Deploying

Each part is deployed with `CREATE2` through the deterministic deployment proxy at `0x4e59b44847b379578588920cA78FbF26c0B4956C`, the same factory Foundry uses, with a zero salt. So a part's address depends only on its code. The compiler knows every address in advance and builds them into the router. The router can only ever reach the exact code it was compiled against.

For a split contract, `lithe compile` prints the deployment plan instead of bytecode, with a note on stderr:

```text
note: `Token` is 602 bytes; split into a router and 2 parts
```

```json
{
  "parts": [
    {
      "name": "Token.1",
      "address": "0x995142bb0A829AfDb6dC92D05D8D9395b12FA5Ca",
      "to": "0x4e59b44847b379578588920cA78FbF26c0B4956C",
      "data": "0x0000…"
    },
    …
  ],
  "router": {
    "bytecode": "0x73…"
  }
}
```

Send each part's `data` to its `to`, in order, then deploy the router's `bytecode` as you would any creation code, with its `deploy` arguments appended. Skip a part whose address already has code: `CREATE2` can't deploy to it twice, and it is already the right code. The router's creation code checks that every part has code, and reverts if one is missing.

An upgradeable router is listed with its own `address`, `to`, and `data`, so it can be deployed through the factory too, at an address known in advance.

A contract that creates a split contract with `defer create` lists that contract's parts in its plan as well. They must exist before it creates anything.

`lithe compile directory` writes the router's artifact to `out/<file>/<Contract>.json` as usual. Its ABI is the whole contract's, because that is what callers use, and it gains a `parts` field listing each part's name, address, and selectors. Each part gets its own artifact at `out/<file>/<Contract>.parts/<n>.json`.

## Upgrades

An upgradeable contract's router is the implementation behind its ERC-1967 proxy. Its upgrade guard is the only way to change code, and an upgrade is still one `upgradeToAndCall`. Parts are deployed first, and deploying them changes nothing until the proxy points at the new router. A `migrate` that lands in a part still runs inside the upgrade.

A contract that grows past the limit upgrades into a split implementation behind the same proxy, at the same address, with the same storage. The reverse works too.

Every upgrade of a split contract deploys a new router, because the router has its parts' addresses built in. A part whose code didn't change keeps its address and is reused. `lithe upgrade-check` shows which parts are reused:

```text
parts
  router  changed
  part 1  unchanged  0x995142bb0A829AfDb6dC92D05D8D9395b12FA5Ca
  part 2  new        0x88a0…

compatible
```

For a split contract, `lithe upgrade` prints the deployment plan with the proxy's `upgradeToAndCall` added, and `--impl` defaults to the new router's `CREATE2` address.

## Cost

A call to an entrypoint in a part costs one extra `delegatecall`, measured at about 2,700 gas: the part's address is cold, and the calldata and return data are copied once more. Entrypoints in the router cost nothing extra. Each part carries its own dispatcher and a copy of any helpers it uses, so a split contract deploys more bytes in total than the unsplit build would have.

## Flags

| Flag | Default | Meaning |
| --- | --- | --- |
| `--size-limit <bytes>` | `24576` | the most runtime code the router or any part may have. Creation code may have twice this, as EIP-3860 allows |
| `--split <auto\|off>` | `auto` | `off` makes a contract over the limit an error |
| `--create2-deployer <address>` | `0x4e59…956C` | the `CREATE2` factory parts are deployed through, for chains where it lives elsewhere |

`compile`, `parts`, `footprint`, `abi-tree`, `upgrade`, and `upgrade-check` take them. With `--split off`, a contract over the limit fails with what each group adds to its size:

```text
contract `Token` is 602 bytes; the limit is 500
  Token                       142
  Ledger                      122
  Pausable                     56
  (dispatch and shared code)  282
```

A contract is also an error when no split can fit it: when a single entrypoint is over the limit on its own, or when the router's upgrade machinery is.
